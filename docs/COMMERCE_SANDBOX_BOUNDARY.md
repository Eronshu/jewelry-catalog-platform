# L02：商城测试身份与环境隔离契约

2026-10-27：本契约L02a已由#51合并至main `2022777`，head CI73/独立审查及合并后CI74通过；本地734项应用/6项支付HTTP模拟与工程检查是该阶段证据。它只交付设计与拒绝回归，不代表L02b新运行模式或L09实际环境已建立。后续本地支付开始模型见 [支付核心](./COMMERCE_PAYMENT_CORE.md)。C架构及冻结V1不变，新模式/配置/路径仍是设计，不是部署或账户授权。

## 1. 当前代码保证什么

- `environment.server.ts` 只接受自有属性 `COMMERCE_MODE=local-test`、HTTP、`localhost`/`127.0.0.1`；有 Origin 时必须精确同源。HTTPS、远程域名、`sandbox`/`live`、伪造转发头都不能启用。它不能证明 DB/R2 绑定身份，也不是认证。
- `workers/app.ts` 在 Admin 路由前验证 Access JWT；路由再 `requireAdmin`。校验使用配置 issuer 的真实 JWKS、RS256、AUD、时间、批准 email/sub 对；服务令牌不能充当经营者。没有可配置的开发登录绕过。测试的合成签名/JWKS 拦截只存在于测试进程。
- `scripts/commerce-local.mjs` 创建临时 DB/R2/配置，强制本机操作，子环境按白名单传递，不继承商家凭据。它不配置真实 Admin 身份。`admin:shell:preview` 仅供表现检查，端点未连接，不能证明授权或数据库写入。
- lab Cookie 是本机测试 capability，当前无 Secure/环境绑定，不是未来游客订单方案。Cookie 不按端口隔离：两个 localhost 端口不能当成两个安全环境。购物车和恢复界面的浏览器存储也不是订单/支付权威。
- 现有 `wrangler.jsonc` 的目录 Preview 不是商家 Sandbox；仓库 CI 只有检查/测试/构建。冻结 V1 描述的自动部署不是当前账户实测：新远程准备前必须核对 Workers Builds、Git 来源、默认分支与预览部署设置，不能从 CI 文件推断无外部自动部署。

## 2. 四类环境及最小资源分离

推荐继续一个代码仓库和现有技术栈，不增加微服务或要求四个 Cloudflare 账户。远程 Sandbox 与未来正式站分别使用独立 Worker、D1、R2、域名及凭据；账号/套餐实际资格与预算后续核对。名字不同不等于资源已隔离，须核对实际绑定。

| 环境                         | 允许的数据与行为                                   | 身份、资源与外部调用                                                                                   |
| ---------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 作品目录 Preview             | 现有虚构品牌/商品；商城关闭                        | 沿用现有目录保护，不导入真实订单；不加载支付凭据、不发送商城邮件                                       |
| 本机自动化/人工虚构测试      | 临时虚构数据、模拟服务商；现有 loopback gate       | 临时 DB/R2；自动化用合成签名，人工表现 fixture 无权执行命令；Google 仍仅显式可选测试配置               |
| 商家 HTTPS Sandbox（未建立） | 虚构顾客、独立测试 SKU/库存、两家实际 Sandbox 交易 | 独立 Worker/DB/R2、Access 应用 AUD、测试账户/应用/Webhook 密钥、允许的测试邮箱；不能读写作品或正式数据 |
| 正式商城（未授权）           | 经批准的真实商品/经营规则及必要顾客资料            | 另建正式绑定与商家身份、正式付款/邮件；无演示数据、测试 Cookie 或 Demo Key；单独上线授权               |

禁止缺省回退：缺 Sandbox DB、R2、AUD、服务商账户/签名密钥或邮件配置时，不能借用作品或正式值。日志、错误追踪、导出、备份/恢复和任务也标记环境、限制访问与收件人。Sandbox 邮件默认不发送，启用时所有交易模板必须经同一测试收件白名单；营销发送不在此项范围。

未来部署预检需用已批准清单核对**实际** Worker 版本、D1 ID、R2 bucket、域名、Access AUD、账户/应用与密钥引用，识别重复绑定；不能只检查字符串前缀。运行时建议核对 D1 内环境标识与预期实例，供发现误接库；该标识及同名环境变量都不能代替账户侧绑定核对，复制的数据库也可能复制标识。后续模型 PR 决定其迁移和故障测试，本轮不加表。

## 3. 四种权限，不互相代用

| 入口                                | 信任来源与后续约束                                                                                                                      | 明确不接受什么                                                                                        |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Admin 查看/恢复/库存/退款           | 真实 Access、环境独立 AUD、批准 email/sub，Worker 与路由双层校验；以后敏感操作再加各自授权/审计                                         | 游客 Cookie、任务 bearer、服务商签名、浏览器自报 email/sub、单有有效签名但 AUD 不同的 JWT             |
| 游客下单与自己的订单查询（L04/L06） | 新的高熵能力/会话，服务端绑定环境、自己的订单与版本；HTTPS 用 host-only、Secure、HttpOnly Cookie，明确 SameSite/到期/恢复；最少返回资料 | 邮箱、递增编号、订单引用、购物车 ID、付款返回参数；旧 lab Cookie 不升级为正式凭据                     |
| 服务商回调（L07/L08）               | 各自验真；核对环境、账户/应用、金额、币种与订单；持久 inbox/业务去重、乱序/重试及核查                                                   | Admin 登录、顾客 Cookie、浏览器 Origin、URL 的 `paid=true`、PayPal approved、仅 IP/路径秘密           |
| 后台到期/核查/通知任务              | 受控平台任务入口与有界持久工作；调用商业命令须保持幂等/版本/审计                                                                        | 公开任意任务 HTTP API、顾客令牌、从浏览器传 DB/时钟/释放数量；不复用本机 expiry bearer 为远程通用权限 |

Sandbox Admin 与正式 Admin 使用不同 Access 应用/AUD，即便是同一个经营者。批准身份应通过受控渠道从已验证登录配置取得，不在聊天、PR、截图或 fixture 中粘贴真实 JWT、Cookie、email/sub 对。仍不做会员/密码库。

HTTPS 游客 Cookie 的 SameSite 建议从 Lax 顶层 GET 返回体验开始验证；返回仍不标记 paid，资料修改/发起付款需同源 POST/CSRF 及自己的会话。实际托管跳转、Safari、返回丢失及跨站 POST 行为由 L06–L09 测试决定，不在此固化未经验证的兼容保证。不同环境使用不同 Cookie 名和存储命名空间；不设置跨子域 Domain，也不把端口当隔离手段。

真实 Admin 浏览器验收优先在单独授权的 HTTPS 测试环境走真实 Access。当前本机 runner 仍拒绝 Admin；不要把测试私钥、JWKS URL 覆盖、fake principal、任意 header 登录或登录隧道复制到运行代码。这样无需为看页面放宽保护；本地开发继续用自动化和明确标识的表现 fixture。

## 4. 后续 HTTPS 模式的配置契约草案

以下是评审清单模板，**不是 Wrangler 文件、环境加载器或已生效开关**。不放实际 ID、身份或密钥值；未来实现需独立 PR。`sandbox` 目前仍返回404，`live` 也没有实现。

| 配置项                                     | Sandbox 要求                                                        | 缺失/不符时的预期                                                     |
| ------------------------------------------ | ------------------------------------------------------------------- | --------------------------------------------------------------------- |
| 环境/模式                                  | 显式 `sandbox` + 不可由请求修改的实例标识                           | 无商业读取/写入；不降级其他环境                                       |
| canonical origin                           | 唯一明确 HTTPS origin；无通配符，回跳地址由服务器固定生成           | 未批准 Host/origin/协议关闭；忽略转发头、客户端 return URL 与查询开关 |
| DB / PRODUCT_IMAGES                        | 独立实际绑定，匹配批准资源清单；schema 版本兼容                     | 在业务数据读取/写入前拒绝；不得回填目录300件作为真实库存              |
| ADMIN_ACCESS_ISSUER / AUD / IDENTITY_PAIRS | 独立应用/批准人，保留现有严格验证                                   | Admin 拒绝；有效另一 AUD 也不放行                                     |
| Stripe                                     | 专用 Sandbox 账户/凭据引用、签名密钥、预期账户/环境、固定服务端回跳 | 关闭该渠道的新尝试；不得尝试 live key 或混用 CLI/托管端点签名密钥     |
| PayPal                                     | Sandbox API、应用/商家/买家、凭据及 Webhook ID 引用                 | 关闭该渠道；不切换正式 API 或把批准当 capture                         |
| 邮件                                       | 默认关闭；专用发送身份和明确测试收件白名单                          | 无配置零发送，拒绝非白名单，不回退正式发件/收件配置                   |
| 新单/新尝试控制                            | 独立可关闭且缺配置默认关闭                                          | 关闭后继续按自己的权限处理既有订单、验真回调、核查、退款与通知        |
| Google / 日志                              | 不默认加载 Google；保存派生地址前完成#37规则核对；日志最少化        | 缺 key 手填可用，不把凭据、地址、Cookie 或原始支付请求落日志          |

远程模式只允许未来评审过的顾客/支付/经营路由，不自动将 `/commerce-lab`、`/_local/commerce/expiry` 或现有测试恢复命令开放远程；它们继续 loopback-only。把服务参数改成 HTTPS 本身不是迁移这些测试命令的方案。L03模型可以在本地推进，暂不依赖这些配置加载器。

Cloudflare 官方说明绑定、vars、secrets 需要逐环境显式配置；本项目还使用 Vite，环境选择和最终生成配置必须一起核对，不能只在部署命令临时加一个环境参数就认定隔离完成。[Workers environments](https://developers.cloudflare.com/workers/wrangler/environments/)（2026-10-27核对）。

## 5. 路由、静态资源和回调分流

未来配置评审必须列全可达入口：测试域名、默认 `workers.dev`、预览/版本别名、旧域名和任何代理。非批准 origin 拒绝商业入口；不需要的别名应在授权配置阶段关闭或证明同等保护，不能凭主域名的 Access 页面推断其他入口安全。

Admin 规范路径、`.data`、嵌套 action、上传/预览，以及大小写/编码别名都必须先经过可信验证，静态产物不能含私有 HTML/数据或占据该命名空间。现有 Worker 会规范化别名，构建脚本也排除 Admin 命名空间的静态文件；但配置的 `run_worker_first` 只列规范路径。直接 Worker 测试和当前字符串匹配测试**不证明实际静态分发、路径规范化和边缘 Access 的组合行为**。保留为远程启用前的真实 HTTP/构建产物验收项；这不是已发现数据泄漏的结论。

建议为两家分别预留 `/commerce/webhooks/stripe`、`/commerce/webhooks/paypal`，本轮不创建路由。它们须可被服务商访问、无浏览器 Access 登录重定向，使用各自验证；不能给整个 `/admin/*` 或所有商城路径加 Bypass 来换取回调可达。若测试顾客页面加测试人 Access，回调分流必须在同一清单逐条验证。公网可达不等于有权改变订单。

Stripe 验签需要未被框架改写的原始请求体；PayPal 消息也需要验证来源，应用订阅与账户/环境需按所选集成核对。[Stripe Webhooks](https://docs.stripe.com/webhooks)、[PayPal Webhooks](https://developer.paypal.com/api/rest/webhooks/)（2026-10-27核对）。后续 resource 不能复用要求浏览器 Origin 的 `readCommerceForm` 来收回调。请求大小/签名时效/重放策略、证书或验证 API 的安全调用和超时由适配 PR 明确，不接受客户端提供任意验证 URL。

只有持久接收/去重后才确认可重试事件已收妥；故障不伪装业务成功。事件去重与交易业务去重分开，订单状态不由回跳改变。具体写入/返回码及失败重试在 L03、L07/L08实现与实际 Sandbox 中验证，本设计不声明已实现。Access JWT 仍需 Worker 验证 issuer/AUD/签名，不能只相信头存在。[Cloudflare Validate JWTs](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/)（2026-10-27核对）。

## 8. 停止和回滚

本 PR仅文档及测试，可撤回，不改 schema/默认配置/运行代码/资产路由/账户；现有商品、购物车、恢复流程继续用原 gate。不要为了让未来配置示例“跑起来”去修改当前mode、导入真实数据或暴露本机端口。

未来运行模式的回滚需保持旧订单兼容：停新订单/新尝试，继续验真接收回调、核查未明付款/退款和履约/通知。单独某家故障只停该渠道新尝试；两家是首版需求，不能自动宣称缺一家也已上线。保留账本/事件/审计及环境映射；不恢复旧库覆盖后来支付事实、不通过撤销密钥或禁收所有回调充当日常停单开关。未完成这些故障/恢复验收不得营业。
