## 2. 总顺序与并行方式

主线按以下7部分推进，优先补齐顾客从商品到订单和托管付款的链路；商品Admin与真实经营资料并行准备，在完整经营闭环前收口。每部分再拆小PR。每个PR完成后停下：提交 → PR → 当前head CI → 独立审查/修复 → 用户或获委托开发者合并 → 核对/更新main与归档清理 → 下一分支。代合并只限无未解决项的小型本地开发/文档PR，不绕过任何门槛。以下表格的一行也可能拆成“模型/服务端、界面、真实验收”多个PR，不把整部分塞进一个大分支。

| ---- | -------------------------------- | ----------------------------------------------------------------- | --------------------- |

商家Sandbox凭据暂缺时，可继续两家适配的契约/模拟故障、后台和通知等独立本地任务；不得把未跑的真实服务商用例勾选通过。Google来源地址的留存核对必须在保存实际Google派生地址之前完成，不能用“顾客确认过”代替。默认保留游客结账，不增加会员/地址簿来解决当前订单问题。

## 11. 每个小PR如何交付、如何暂停

每个任务有一位开发责任人、明确文件/接口范围；经营动作由小姨验收、预算/发布由你批准。只在边界独立且有明确授权时委派；当前仍按一个已审查合并结果再开下一分支，不堆叠。

共同完成定义：必要说明/迁移与实现齐备 → 有意义的成功/异常/并发测试 → format/lint/typecheck/tests/生产构建 → 当前head独立审查（特别库存/支付/退款/权限）→ CI → 无未处理发现 → 用户合并。环境/业务/真实服务商/真机的未完成验收单列，不能用mock补勾。仅文档PR不新增镜像实现的测试。

共同回滚规则：未合并保留分支；已发布先关闭问题**新操作**，使用兼容代码回退并保留已有订单/支付事件/退款/通知任务。数据库新增字段/表优先向后兼容，不能回退代码时删交易、恢复旧余额或禁收既有Webhook；补偿与重放是有审计的独立动作。每个功能PR补具体停止开关、数据影响和演练证据。

首版继续后移：缺货收款/积压额度、完整采购ERP、多仓、完整FB订单/财务同步、会员/地址簿、优惠积分、自动采购/营销和自动运费标签。保留两种支付、三种交付、必要售后/恢复，不为赶时间暗中削减已确认业务目标。
