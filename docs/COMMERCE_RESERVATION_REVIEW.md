## Boundary and contract

`GET /admin/commerce/review` requires the Worker's existing approved-human Cloudflare Access JWT verification and the route's own `requireAdmin(context)`, then the explicit loopback commerce gate, before any D1 access. The expiry bearer is **not** an Admin identity. The standard fictional runner supplies no Access configuration and does not bypass it; default/remote commerce availability stays disabled. Synthetic test keys and intercepted JWKS are used only in integration tests, not runtime authentication settings. Authorized browser/merchant UAT still needs a separately reviewed local test identity setup.

The resource returns `private, no-store` and `noindex, nofollow`. Only GET is supported; mutation methods return405/Allow:GET after authorization/gating without storage access. It accepts:

- No query: up to25 attention rows and an optional `{ reserveUntil, orderId }` continuation cursor. The indexed query returns at most26 candidate rows in stable deadline/ID order; D1 can scan additional indexed entries to evaluate the time/payment predicate, so this is not a26-row billing/read-cost guarantee. Scope is **pending-payment orders that are overdue or have started payment, plus held fulfillment**. It is not an exhaustive future payment-audit queue or proof a failed expiry task ran.
- `after`: JSON encoding of the returned cursor, at most160 characters. Only its two fields, valid nonnegative safe timestamp and order reference are accepted. Pages observe current state independently; newly eligible rows behind the cursor appear on a fresh traversal. A cursor is not a customer credential or a point-in-time audit snapshot.
- `reference`: exact validated internal order reference. An approved operator can inspect any matching test-order state, without the original lab cookie. Missing reference returns generic404. No partial/email/owner search; duplicate/unknown parameters or combining reference/after returns400 without storage access.

The list projects only order reference, order/payment/fulfillment states, deadline, version and reason codes. `overdue_unpaid` is a need to inspect actual stock/driver history, not proof release occurred. `payment_review` means the pending order has any state other than not_started; a developer must reconcile payment facts before release/new attempts, and no provider verification is performed here. `fulfillment_held` requires owner investigation of fulfillment/stock and later payment facts, never automatic reopening. These reasons can overlap. Current no-payment test records do not establish production incident procedures.

Exact inspection additionally selects only variant ID/quantity/position (at most20 lines) and the latest25 transition kind/time/expected-version summaries, plus a truncation flag. No quote snapshot, contact/address, owner hash, cookie, provider identifiers or capability is selected. An unexpected over-limit line set fails closed. Storage failures return503 with a generic message; application errors do not echo submitted values and application code does not log raw exceptions/inputs. Infrastructure access-log policy still needs review before storing customer data. There is no customer-facing proof-of-ownership recovery: knowing an ID/email does not grant access.

Migration0007 adds only operator-list/history indexes. The resource performs SELECTs, including a bounded detail batch; it does not release stock, change payment/order state, reassign session ownership, refund or send notifications. Human investigation and subsequent recovery commands need a separate design/PR with audit, confirmation and current-state checks.

## Owner screen (C06b2a UI)

This feature branch adds `GET /admin/commerce/reservations`, retaining `/admin/commerce/review` as the compatible JSON resource. Both share the same server-only request boundary: approved-human Admin principal, explicit loopback mode, validated reference/cursor, then the existing minimal SELECT-only model. The screen and its `.data` requests are Worker-protected; documents/data/errors are private/no-store and noindex. Mutation methods stop with405/Allow:GET without loading records. There is no new migration, provider request, customer capability or runtime identity bypass.

The local Admin welcome page shows **Review test reservations** only when the root local-commerce flag is true; the screen independently enforces authorization and availability. It offers up to25 attention records per page, exact full-reference GET search, current-page refresh and First page navigation. A new traversal finds newly eligible rows behind a cursor. Empty/error results never claim all orders are paid or stock was released. During refresh/navigation the previous observation is marked pending; a failed refresh replaces it with a generic error, not a successful-looking stale list. Response values and raw exceptions are not echoed in error text.

English labels explain stored order, payment and fulfillment states independently. Deadlines and last observation use Toronto time, with machine-readable times. Overdue unpaid work goes to the developer for driver/stock-history inspection; payment activity goes to the developer for reconciliation before release or a new attempt; held fulfillment goes to the owner with developer support. No button releases stock, changes a state, refunds or transfers a customer session. Detail shows only item references/quantities, record version and the latest25 transition summaries; it is not a full stock audit or customer receipt. No product-name enrichment or financial report is claimed.

The isolated `tests/admin-shell-preview` fixture supplies fictional list/detail/empty/unavailable scenes and never imports the runtime route, Access configuration or D1. It is a presentation tool, not an authenticated Admin environment.
