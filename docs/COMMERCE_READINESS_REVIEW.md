### 2.2 现货、Facebook 留量与收货

1. **现货公式：** on_hand 是账面已验收合格、尚未登记交出的实物；网站可售量 = on_hand − Facebook 专用留量 − 网站临时预留 − 网站已确认分配。全部非负，所有占用之和不得超过 on_hand。Facebook 已售未登记期间账面会滞后，该件仍隔离在 FB 留量中，不能调回或再次承诺；登记时同时扣 on_hand 和 FB 留量各 1，不再扣网站可售量。已登记数据必须可与实物盘点核对。
2. **Facebook 隔离：** 用户确认先留 1 件；建议在小姨指定的 FB 在售颜色/SKU 上划出 1 件，不按整款跨颜色共用、不替所有 SKU 自动留量。从网站空闲现货原子划转，不能抢已预留/已付款件。初次划出、补留、调回都需原因与库存校验；没有足够空闲货则拒绝。销售/调回前核对实物并登记之前成交，不自动补到 1，不用“永远总库存减一”冒充账本。
3. **仅售现货：** 网站可售量不足即阻止相应数量购买，前台按钮与服务器都校验。可显示 Sold out/Out of stock，但该颜色缺货不导致其他有货颜色失效。首版不创建缺货额度、预售付款、混合待补订单或自动候补；采购在途和隔离不合格货不增加可售量。
4. **结账预留：** 加购物车不锁库存；提交最终报价时一次性创建订单/快照并预留所有行。任一行不足则全组失败，不产生半组占用。请求幂等和数据库条件约束必须经本地 D1 并发测试；FB 调拨与网站最后一件购买不能同时成功。
5. **到期与付款：** 临时预留期限与服务商会话/查询策略一起验证；已确认分配不自动到期。支付未知先查询并限制新尝试。释放后收到真实成功，先进入 held 异常，仅可从网站空闲现货按原承诺重新分配，不偷用 FB 留量；不能满足则由小姨及时联系并处理退款，不能擅自转成等待进口货的预订。
6. **收货：** 首版只保留简单验收/入库，不做采购 ERP。小姨核对到货及来源，按实际合格数量一次入库；不合格隔离、短发另记供应商问题，重复收货键不得重复加库。验收完成前仍不可购买；进口运输不能触发顾客发货通知。新货不自动填 FB 留量，不自动恢复取消订单或清除已有缺货异常。
7. **履约与盘亏：** 网站已确认订单先有现货分配，交付时同时扣实物与对应分配一次；付款不另扣实物。若发现损坏/盘亏已影响分配，暂停该 SKU 新销售及受影响履约，小姨核实并联系顾客，处理可履约的现货或取消/退款。不能隐藏差异、无货发出或把异常当常规缺货接单。

D1 的 [batch 文档](https://developers.cloudflare.com/d1/worker-api/d1-database/)描述批量执行及出错回滚；这不证明条件更新 0 行会自动使整个业务操作失败。C01/C06 必须验证全有或全无，不直接复制图片 batch 当作库存原子性证明。

### 2.3 独立状态与金额

以下为内部状态建议；Admin 显示通俗英语，并解释下一步，不能用单一“订单状态”混合所有流程。

| 维度        | 状态 / 转移要求                                                                                                                                                                                              |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 订单        | pending_payment → confirmed → closed；也可 cancel_requested → cancelled。取消请求立即阻止履约，只有取消处置落账才结束；已交付订单的退款不自动变成未交付取消。                                                |
| 履约        | 付款和现货分配核验后 ready_to_pack → packed → ready_for_pickup / out_for_delivery / shipped → completed；held 用于盘亏、迟到付款或风险等异常。首版无常规 awaiting_stock 队列；恢复 held 必须复核现货与付款。 |
| 支付尝试    | initiated、action_required、approved/authorized、processing、succeeded、failed、cancelled、expired、unknown。批准/授权并非成功收款；退款和争议不是把成功交易改写成失败。                                     |
| 退款        | requested → pending → succeeded / failed，查询不明为 unknown；金额可部分或全额。已成功及尚未确定失败的退款均占用可退余额，防止并发超退。                                                                     |
| 争议 / 风险 | 独立标记与处理记录；付款成功仍可能需人工暂停履约或应对争议，不改变历史收款。                                                                                                                                 |

服务器按当前有效规则校验数量、可售性、交付地区、地址与报价，计算整数分金额和统一舍入；建议首版不做优惠券。报价绑定版本、币种、过期时间与顾客同意；服务商地址/运费/币种不能在托管页被改成本站未批准的值。若产品强制提供不同地址，必须验证/重新报价或停止该尝试。已创建支付尝试对应的金额不可偷偷更新。

支付转换须核对订单、报价、账户、环境、交易 ID、金额与币种。每订单最多一个有效进行中的尝试；重试优先查询原尝试，未明状态禁止换渠道再次扣款。仍可能出现服务商延迟或跨渠道重复收款，必须检测多笔 capture，冻结额外履约并由小姨确认退款；不能承诺跨服务商的绝对一次扣款。

取消先锁定履约，区分未收款释放、待支付核验、已收款退款、已发出转售后。退款必须有授权和可退余额检查；由开发者设计幂等提交/查询，小姨处理金额和原因。退款成功不自动增加库存；退回商品经检查后才能入库，尚未交出的分配在取消成立时只释放一次。退款、取消或发货请求并发时只能一种合法转移成功。

### 2.4 Facebook、权限、通知与对账

- **Facebook：** 首版只支持上述留量和最小售出/调拨登记，不做 FB 顾客资料、付款链接或完整订单系统。记录 SKU、数量、来源参考和时间，重复请求不能二次扣库。外部成交金额和退款由小姨另记经营账；误卖网站保留件必须进入盘亏异常，不能静默扣走已付款分配。完整渠道订单后续再立项。
- **权限：** 小姨经营角色处理订单、收货、退款和盘点；开发者默认无真实顾客/退款权限，紧急访问限时授权且留痕。未来新增员工时再细分，不先建设复杂 RBAC。服务端逐操作授权、禁止人工把线上交易直接改为“已付款”；退款/导出/盘点调整需明确确认和原因。
- **通知：** 建议首版邮件涵盖订单确认、付款未明、延期、取消/退款结果、可取/送货/发货。业务变更与 outbox 同事务记录；发送失败重试和告警，保留可供小姨使用的替代联系方式。不承诺邮件只送达一次，消息应能识别同一订单/版本，重复不能重复履约。后台进口“在途”绝不触发顾客发货通知。
- **对账：** 每日核对网站订单 capture/退款、费用、服务商结算和银行到账，总销售额不等于当日净到账。FB 成交由小姨另行记账，并核对 FB 库存售出记录；网站报表明确仅含线上交易。先用受保护报表和人工核对，不建全店总账系统。

## 3. 异常责任与停止办法

| 异常                              | 经营处理人                                             | 技术处理人 / 必须动作                                                            |
| --------------------------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------- |
| 供应延迟、短发、不合格、无法供货  | 小姨联系供应商、验收入库，未到货保持不可购买           | 开发者保证在途/隔离货不入可售量；首版没有因此等待供应的正常已付款订单            |
| FB 晚录、错卖、盘亏或已付款无分配 | 小姨核对 FB 实物/成交和线上承诺，必要时联系顾客        | 开发者冻结受影响履约/新售，查账本；不自动补留或把异常改成预售                    |
| 付款超时、重复/迟到支付、金额不符 | 小姨在异常队列核实，不重复收费或发货，决定额外收款退款 | 开发者查询服务商、重放已验证事件、修复状态；保留审计                             |
| 退款未知、退款失败、争议/欺诈     | 小姨负责财务决定、顾客沟通与争议材料/截止日            | 开发者保护退款额度、查询/告警；不因超时释放额度重退                              |
| 通知丢失、自取未到、投递失败/丢件 | 小姨人工联系、记录交付与售后决定                       | 开发者修复通知重试，避免把通知成功当作交付成功                                   |
| 数据损坏、密钥泄露、不可用        | 你协调、小姨暂停新单并安排顾客沟通                     | 开发者关新结账、保留回调/退款/对账，轮换凭据、恢复及核对；按适用流程处理隐私事件 |

上线前 D07 记录实际负责人、代理人、告警渠道与响应时限。无人接管的异常不允许静默“自动成功”，临时停止新单不免除旧订单责任。

## 4. 安全与隐私边界

| 风险           | 首版设计 / 验收要求                                                                                                                                                                                      |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 卡资料与密钥   | 托管付款；本站请求/数据库/日志/Git 不接收卡号、有效期或 CVV。服务端密钥和 webhook secret 分环境受控存储，最少访问、轮换和泄露响应；不让用户发到聊天。PCI 等适用责任由服务商/收单方核对，托管不等于免责。 |
| Webhook 与伪造 | 两家独立端点按官方流程验签，Stripe 保留原始 body；核对环境/账户和已绑定交易。只在持久化接收成功后确认接收，处理失败可重试。服务商事件端点不能被 Admin Access 登录挡住，也不能因此放开 Admin。            |
| 金额和请求     | 服务器重算、限制数量/请求体、校验币种/地址/规则版本；浏览器回跳只查询，不记账；服务端安全返回 URL，限制跨站请求、会话重放和恶意刷单占库。                                                                |
| 幂等与乱序     | inbox 唯一键包含服务商、环境、event ID；业务 transaction ID 另去重。重复/逆序事件不能倒退状态；失败可重放但不可重复扣款、分配、退款或发货。未知状态主动查询，定时扫描不依赖单次回调。                    |
| 库存竞争       | 所有来源走同一原子命令，库存与渠道隔离约束在数据库层校验；检查版本并测试多行失败回滚、取消/付款/到货竞争。                                                                                               |
| 权限与隐私     | 沿用现有 Access/JWT 和同源写边界并覆盖新 API；顾客查询用高熵凭证或验证流程，不可枚举、不公开缓存。地址/联系方式最少收集，URL/日志/监控不含敏感资料；导出限权、保留和删除/匿名化规则需核对法定记录义务。  |
| 欺诈与争议     | 速率限制、异常多次付款/地址提示、小姨复核/暂停履约、保存必要同意和交付证据；不把风控评分当作无争议保证。                                                                                                 |
| 可靠性         | 持久 inbox/outbox + 可重试后台任务/定时扫描，后台任务崩溃可续做；不能只靠内存、一次 waitUntil 或邮件。简化架构但保留恢复能力。                                                                           |
| 备份与恢复     | 独立环境演练 D1/R2、配置和审计恢复，确定恢复点/时长目标；恢复后与服务商补拉交易并对账，不能恢复旧数据库而忘掉已收款/已退款事实；恢复不自动重发货。                                                       |

2026-10-16 公开技术资料核对：[Stripe Webhooks](https://docs.stripe.com/webhooks)要求签名验证并说明重复/乱序处理；[PayPal Webhooks](https://developer.paypal.com/api/rest/webhooks/rest/)提供验证流程。具体事件、重试、幂等保留期、API 版本和托管交互仍需在 C10/C11 按实际集成验证；没有把公开文档等同于本项目通过验收。

## 7. 完成边界
