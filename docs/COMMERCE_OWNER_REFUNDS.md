# Owner Stripe full-refund test — Issue #93

Local implementation only. C and frozen V1 are unchanged. This first visible refund slice uses an explicit **test assumption**: at most one full Stripe refund intent per canonical capture/order. It is not the shop's cancellation/return policy. PayPal refunds, partial refunds, audited stock disposition and return inspection follow separately; this slice cannot pass the complete C12/L15 launch gate.

## Operations and boundaries

From protected order details open **Refund status and test refund**. The page shows the original captured CAD amount, verified refunded amount and current saved status. The owner explicitly confirms the full amount. A persisted intent locks any further packing/handoff, including when the request is pending, unknown or definitively failed. Already recorded handoff is historical and is not undone. No item is automatically restocked or released; physical return/inspection and a future audited stock action are separate.

The only runtime transport is behind existing approved Admin, loopback instance, separate UI/write/query opt-ins and exact same-origin forms. Browser amounts, charge/account IDs or destination methods are not accepted. Refunds bind the original canonical actual-account Stripe capture, charge, PaymentIntent, Session, amount, request UUID/key and original metadata. No actual customer/contact data or new card handling is added. This is not a postage, notification or business policy feature.

Migration0026 appends immutable refund intent/dispatch/observation audit and extends the0025 fulfillment eligibility view by excluding a refund intent, retaining its original financial predicates. It does not rewrite capture facts, order payment history, stock balances or existing financial/fixture fences. There is one database winner per capture/order. Durable positive write acknowledgement and exact original readback precede the single external mutation; lost acknowledgement consumes dispatch permission and never authorizes another POST.

The adapter fixes `https://api.stripe.com`, test credentials, `2026-10-28.endive`, bounded10s/128KiB requests and manual redirects that are rejected rather than followed. It has no default fetch. An external POST response may recover a refund ID, but does not establish success. Fresh account, original PaymentIntent/Charge and refund reads must match the complete association, full CAD amount and refund metadata. Success requires canonical refund success and the charge's full refunded amount. Refund objects do not require an invented `livemode` field; test mode is verified on PaymentIntent/Charge and fixed test credential/account boundaries. Official contracts checked2026-11-02: [create](https://docs.stripe.com/api/refunds/create), [retrieve](https://docs.stripe.com/api/refunds/retrieve), [list](https://docs.stripe.com/api/refunds/list), [refund object/statuses](https://docs.stripe.com/api/refunds/object). No fees, bank-arrival time or legal conclusions are asserted.

## Unknown results and access

The browser saves only original UUID/order/version/acknowledgement before start. Double click shares one start; timeout/remount never automatically re-submits. **Check saved request** is local readback; **Check Stripe refund status** performs bounded canonical reads. Lost IDs are searched by the original charge/key/metadata, at most three pages of100; absent, ambiguous or incomplete evidence remains for review. Never use a new key or a different amount to resolve uncertainty.

An Admin page can recover the original request ID and original request version from the database for an explicit query across devices; no reconstructed request is permission to re-POST. Other Admin identities cannot impersonate the original actor. Corrupt browser storage, mismatched receipts, authorization failure or unreadable history require developer recovery. Even a definitive failed/canceled provider status leaves the first slice locked for manual review, rather than silently starting a second refund.

The private customer order authenticates its original session and scoped ownership first, then returns only refund state, original amount and verified refunded amount. It does not expose request UUID, actor/account/charge/PI IDs or operation keys. Existing refund history remains visible **independently of Admin UI/write/query flags**; a failed history read fails closed rather than falling back to a plain confirmed-payment presentation. Refund status suppresses stale payment widgets. This is a recorded test result, not a bank-settlement promise.

## Local setup, stop and rollback

`COMMERCE_LOCAL_REFUNDS=1 npm run commerce:local` sets local Admin refund UI/write/query opt-ins. An eligible paid Stripe order and the separately authorized existing private0600 external Stripe Sandbox file are needed to actually send a refund. This flag supplies no credentials, Admin login or auth bypass. Default runs do not send provider requests. The standard runner creates a new temporary database; restarting it does not recover an older one.

Pause new refunds by removing `COMMERCE_OWNER_REFUND_WRITES`; keep original scope/database/configuration and `COMMERCE_OWNER_REFUND_UI`/`COMMERCE_OWNER_REFUND_QUERIES` for Admin recovery. Local lookup remains available with writes and external queries paused. Disabling Admin UI hides owner controls but does not hide the customer's recorded refund. Preserve migration0026, all intents/dispatches/observations and financial/stock history. Do not restore old balances, delete requests or change keys to undo a refund. Unknown outcomes require same-association reconciliation; real returns need a later separate audited workflow.
