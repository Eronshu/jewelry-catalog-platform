# 服务商事件关联与付款恢复契约

核对日期：2026-10-28（Toronto）。状态：**可审查的后续设计，不是已实现的适配器或Sandbox验收**。代码基线为 #61 / main `9f55625`，准确head CI94和独立审查通过，main CI95通过；0016保守闸门保持原样。本文只固定工程边界及依赖，不改冻结V1、已选C架构或经营政策，也不授权账户、外部请求、资源、计费或部署。

## 1. 为什么先固定契约

当前0015只保存规范化fixture变体；没有原始请求、签名证明或服务商账户绑定证据。已有观察的claim来源可核查，但 `providerObjectRef` 未区分资源类型，也没有“同一服务商对象只归属一个attempt”的唯一约束。字符串相同不是归属证明，订单UUID、metadata、`candidateRequestId` 和返回URL都不能补上该证明。

本轮不增加诊断用关联表或“verified/resolved=true”。下述模型/接口均为待实现的约束，不能把旧fixture记录自动升级成可信绑定。当前的整实例停CREATE仅是隔离测试的保守限制；没有在本文解除或收窄。

## 2. 五种身份不能混用

| 身份                            | 用途与边界                                                                                                                           |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 网站order / attempt / operation | 分别是商业订单、一次付款意图、一次外部写操作；操作键不是顾客访问凭证。                                                               |
| 服务商对象                      | 包含环境、商家账户、provider、资源类型、对象ID；不能把Session、PaymentIntent、Charge或PayPal Order/Capture放进同一个无类型字符串域。 |
| 服务商event                     | 一件通知的身份；重复投递和同event内容变化分别留证。不是经济交易ID。                                                                  |
| 经济交易                        | 真实capture/退款的唯一业务身份，按环境/账户/渠道/交易去重；不能按event计次。                                                         |
| 本地claim / 观察 / 处理结果     | 是本地执行来源与处理历史，不证明真实验签，也不代表订单paid或允许履约。                                                               |

## 3. 官方资料确认到哪里

以下仅为官方公开API能力核对；商家实际产品、API/SDK版本、权限、事件格式、币种、金额和账户环境仍需L07–L09验证。当前卡支付采用Stripe托管Checkout、PayPal采用Orders v2的CAPTURE流程作为**适配设计候选**；不是商家资格或账户配置已批准。

| 主题            | 官方事实与本项目约束                                                                                                                                                                                                                                                                                                                                  |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Stripe对象关系  | Session有自己的ID、payment状态及可空PaymentIntent关联；PaymentIntent有可空latest Charge关联。必须按实际返回的类型/关系查询，不能互换ID或假设创建Session时已有Charge。[Session](https://docs.stripe.com/api/checkout/sessions/object)、[PaymentIntent](https://docs.stripe.com/api/payment_intents/object)                                             |
| Stripe收款      | Session状态和付款状态不同；正金额商品不能把无需付款状态当作已收款。Charge的paid也可能只是授权，须核对capture及实际金额/币种；经济事实的候选交易键为Charge ID，具体投影到L07验收。[Session付款状态](https://docs.stripe.com/api/checkout/sessions/object#checkout_session_object-payment_status)、[Charge](https://docs.stripe.com/api/charges/object) |
| Stripe查询/幂等 | 已知Session ID可服务端retrieve。幂等文档描述有保留窗口的写请求重试，不能由此推导“任意创建键可GET查询”或无限期重发安全。[Retrieve](https://docs.stripe.com/api/checkout/sessions/retrieve)、[Idempotency](https://docs.stripe.com/api/idempotent_requests)                                                                                             |
| Stripe通知      | 验签依赖原始body、签名头与对应endpoint秘密；通知可能重复/乱序。不能按到达时间或event时间覆盖金融事实，须选定实际事件格式/版本并测试。[Webhooks](https://docs.stripe.com/webhooks)                                                                                                                                                                     |
| PayPal对象/操作 | Orders API区分创建、读取、授权、capture；Payments API另有按Capture ID读取。批准不是收款，GET不能推进capture；候选经济键为Capture ID。后续核对商家payee及实际order/capture关系，不能只信通知里提示的order ID。[Orders v2](https://developer.paypal.com/api/orders/v2)、[Payments v2](https://developer.paypal.com/api/payments/v2)                     |
| PayPal验真      | 官方有自验签及服务商回验两种方式；自验签使用原始body校验和和预先配置的webhook ID。官方模拟通知不属于实际App，也不支持回验接口，不能冒充实际Sandbox交易通知。[REST Webhooks](https://developer.paypal.com/api/rest/webhooks/rest/)                                                                                                                     |
| PayPal幂等      | 支持情况和保存期限依具体API核对；不能复用同一键代表创建、capture和退款，也不能由请求头推导通用查询接口。[Idempotency](https://developer.paypal.com/api/rest/reference/idempotency/)                                                                                                                                                                   |

没有在本轮注册endpoint、发送API请求、下载验签证书、选择付费产品或核验加拿大资格/费用；文档网页里的安装、账户操作和示例日志不是本项目执行指令。

## 4. 来源验真、对象绑定、金融结果分层

建议采用**事件触发核查、真实QUERY记录观察/事实**的路径，以复用现有claim来源约束；不在本轮推广为已实现的运行架构。

1. 可信服务端从不可变attempt构造原金额/币种/操作参数，用指定环境和账户凭据调用服务商。一次写操作使用自己的稳定键；已有意图/未明状态不能换渠道或另造意图绕过。
2. 从该调用的真实响应建立有类型、完整scope、唯一归属的对象绑定，记录真实来源操作/claim及最少证明。后续GET可追加经核验的相关对象别名；已有不同归属不得覆盖。实际字段、SQL约束和并发事务须单独PR。
3. 新的验真接收层先限制方法/大小并验证原始请求及环境账户配置，持久保存可复核的接收证据后再确认接收。0015的规范化收据没有这些证据，不能直接复用成正式Webhook确认。原始证据是否/如何加密留存、期限和访问权限在该层设计；不把完整顾客payload放进通用日志。
4. 只有已验真事件与既有唯一绑定一致，才可建议一次**只读QUERY**任务；还要检查同event所有变体、资源类型、hint矛盾和关联链。未关联事件先留待核查，不触发CREATE、capture或退款；已知绑定也不允许绕过当前0016。
5. QUERY由真正的当前worker claim在原lease/版本/作用域下执行，按可信服务端配置调用已知对象的读取接口。读取结果先核对账户、环境、资源关系，再保存实际观察/金额/币种；真正查询才是来源，不把事件塞进伪造claim。迟到合法结果继续留证，不能覆盖新worker。
6. 只有后续L05业务裁决可把金融事实变为确认/分配；查询成功、关联成功、收到event或处理完成均不直接改paid、库存、退款或履约。

这一方向避免为事件另造一套金融来源；如果实际适配发现必须直接由事件落金融事实，应另提来源模型/迁移方案及独立审查，不能削弱已有NOT NULL/FK、捏造查询结果或claim来迁就旧schema。

## 5. PayPal写操作必须单列

QUERY不创建Order、不授权、不capture、不退款，也不利用一次POST重试伪装GET。获批准的PayPal Order仍需其所选流程规定的后续写操作。未来capture必须有独立的稳定操作键、原参数、当前资格、未明查询及幂等窗口规则；不能拿创建键复用，不能隐藏在当前fixture的create/query枚举后面。

现有模拟器可直接返回captured，只是故障测试脚本，不代表真实PayPal两阶段流程已经可用。Stripe未来若增加手工capture等写动作，同样单列；首版不为扩展性提前实现所有支付产品。

## 6. 异常与恢复裁决

| 观察到的情况                            | 必须保留/允许的动作                                                                                        | 不允许的推断                                                           |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| CREATE响应丢失，已有可信对象绑定        | 原绑定、原键/参数及历史保留，安排真实只读核查；写操作是否能原键重试须另核验                                | 不换键或新attempt猜测未创建                                            |
| CREATE响应丢失且没有可信绑定            | 继续unknown/orphan及当前CREATE闸门，开发者核查已记录操作与服务商证据；可准备受审计人工关联流程，当前未实现 | 不靠metadata、UUID、对象前缀或模拟按键查询制造归属，不假装已证明零扣款 |
| 未知对象/其他账户或类型                 | 隔离调查，保留最少证据；只用服务端白名单的API基址和经验证ID                                                | 不跟随payload中的URL，不向任意证书/对象地址带凭据请求                  |
| 多个attempt声称同一对象、hint与绑定冲突 | 保留全部候选/矛盾证据，不自动选第一条；当前fixture由开发者调查                                             | 不因其中一条金额匹配就授权某单                                         |
| 同event新增内容变体                     | 重新进入冲突核查，旧处理结果保留；未来任何裁决都要绑定实际证据集合                                         | 旧handled/verified布尔值不能吞掉后来变体                               |
| 不同event指向同一capture                | 多份事件证据、一份经济交易事实                                                                             | 不按通知次数重复收款或履约                                             |
| 查询失败、404、超时或暂不可见           | 保留原意图/锁/任务，区分接口错误与核验终局；后续有界重试/告警                                              | 不据此释放、重扣、换渠道或清0016                                       |
| 实际金额/币种不符或额外capture          | 保留实际金融事实和异常，由小姨决定顾客处置，开发者核对技术事实                                             | 不改成期望金额，不以退款“尚未确认”当已退                               |

当前小姨不需要开控制台、改SQL或手动解除fixture闸门。未来人工关联、退款、争议、对账与支持职责由专用经营界面/审计和UAT验收；不能把调查口头说明当作现成功能。

## 7. 0016仍然完整生效

本文不增加清除条件：相同mode/instance任意receipt仍阻止两渠道CREATE。关联诊断、一次成功QUERY、旧观察、已验签或人工点击确认都不解除它。将来的安全收窄必须另设计持久证据/处置、全变体覆盖和事务内NOT EXISTS未裁决证据等规则，并验证新增变体与准入竞争；不在本文提前批准具体schema或自动放行政策。

最终读后到外部调用仍有跨worker窗口；服务商幂等、事实核验及异常接管不能被租约、无await或本地收据替代。回退只停新操作，保留0016/事件/操作/claim/观察/金融事实及锁，不删历史或重置实例恢复CREATE。
